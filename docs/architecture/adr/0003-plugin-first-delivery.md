# ADR 0003 第一阶段开放第三方，功能以插件交付

日期：2026-11-07。状态：用户已确认的产品与架构决定；实施和技术验收尚未开始。

## 决定来源

用户在“先自用还是第一阶段开放第三方开发/安装/分发”的选择后明确回答：“第一阶段就支持，我们的功能开发也围绕插件化进行这样会很通用”。

据此关闭C-07，新增F-EXT-05（第一阶段第三方开发/安装/分发）和F-EXT-06（第一方功能使用公开插件契约）。本决定调整 [ADR 0002](0002-extension-boundary.md) 的分期，不改变Core数据所有权、统一事务与权限约束。

## 采用的架构

- Core负责共享数据、不变量与应用服务；Host负责平台承载、隔离、授权、包生命周期和恢复。
- 产品工作区、阅读/笔记/学习等用户功能通过插件贡献与公开宿主能力组合。需要原生渲染的底层服务位于Host adapter，不给官方功能插件开放私有直连。
- 官方功能与第三方消费同一版本化SDK，使用同一注册/安装/授权/升级链路。预装是包来源，不是特权或另一套插件API。
- 第一阶段支持实际外部插件包的构建、分发、安装与更新；独立作者无需修改QUSOR源码或重编译主程序。至少具备可实现来源/处理逻辑的受限执行profile，不能仅用主题配置证明达标。
- 发布SDK含协议/schema、类型或绑定、manifest、错误/权限/兼容规范、作者文档、构建打包与本地验证方法。SDK工件可独立使用，不依赖主仓库相对路径。
- 最小分发先具备用户主动取得包后的安装与手动更新。中心插件市场、收费、后台自动更新可单独安排，不是开放第三方的前提。
- 每个承诺首发的平台/渠道都验证对应第三方能力。移动执行未验证是发布阻断，不自动退回仅内置、静态模板或缩减平台范围。

## 实施顺序

M-1先证明所选运行方式、协议、隔离、平台/渠道和独立插件包可行性。M0先交付SDK/Host/包管理/贡献UI/统一入库纵向基础，再经同一公开路径开发正式功能插件。

具体任务EXT-B01–B08与EXT-P11–P13见 [交付计划](../extensions.md#12-第一阶段交付顺序与发布门槛)。独立包闭环、权限隔离与SDK边界是M0功能开发的前置；当前不创建SDK空壳或业务占位实现。

## 验收

1. 从独立工程只用SDK与公开文档构建包，在未改动的宿主中安装。
2. 官方功能包以普通插件身份完成同一旅程；移除特殊授权后限制真实生效。
3. 同一包类型支持安装、更新失败恢复、禁用和卸载；不改写Core schema或丢知识。
4. 功能插件依赖检查不可到达application/storage/NSH私有实现。
5. 旧SDK兼容策略、包篡改/身份接管、资源耗尽、跨库越权和移动生命周期有实测记录。
6. 停用后Core通用查看/完整导出恢复可用，插件管理和故障修复入口仍存在。

## 影响与保留事项

插件基础从可选扩展提升为首版关键路径，原M-1/M0时间需重估。SDK只公开真实功能所需的能力，避免先建设无消费者的通用平台。

当前仍是架构基座阶段，无业务实现。该决定不自动确认Reader AI/画布/同步进入首版，不决定云端默认行为，不承诺RSS/微信读书具体插件已可接入，也不选择运行时库或公开许可证。C-02/C-03/C-04等原有未决项保留。
