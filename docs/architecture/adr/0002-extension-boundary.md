# ADR 0002 将插件扩展作为基座能力

日期：2026-11-07。状态：采用扩展边界；后续分期已由 [ADR 0003](0003-plugin-first-delivery.md) 更新为第一阶段开放第三方、第一方功能插件化。具体SDK字段与执行运行时待技术验证，不代表插件功能已实现。

## 背景与需求来源

用户明确要求支持插件化以长期扩展功能，举例RSS与微信读书选段加入知识库，并强调这些只是例子。该要求改变的是架构基座，不是授权本轮实现RSS、第三方账号接入或插件市场。关联 F-EXT-01 至 F-EXT-04、F-SRC-01、F-DATA-01、F-AI-03。

现有Core独立、不可变来源、统一事务和AI审核原则继续适用；不能通过“插件自由度”产生数据所有权或写入旁路。

## 决定

1. 采用独立Extension API与宿主broker。扩展通过版本化贡献点与core-api协作；Core不依赖NSH或插件运行时，第三方不绑定Rust动态ABI。
2. 扩展点覆盖来源、选区动作、命令、声明式视图，并为导入导出、处理器、检索、Agent工具和阅读/可视化保留分级能力目录；按真实用例逐步公开。
3. 所有正式知识由Core持有。外部选文保存本地不可变快照与QLA，另存外部来源及导航能力；插件卸载后仍可读、检索、引用和导出。
4. 宿主绑定身份并执行能力授权；manifest、签名和进程隔离均不单独构成安全沙箱。委托权限只能缩小；网络、凭据、资料读取与写入分别控制。
5. 用户明确收录可以一次提交；AI修改继续候选审核与撤销。最终业务写入、回执、审计及可同步投影经过同一应用事务。
6. 插件契约与运行/分发策略分开。按ADR 0003，第一阶段须验证第三方独立包与实用受限执行能力；官方预装包与第三方消费同一SDK。移动运行/渠道仍须实测，不以仅内置替代。
7. 当前不新增空crate或runtime依赖。未来模块、CaptureDraft、Schema增量、生命周期与验证任务统一见 [插件架构](../extensions.md)。

## 不采用的方案

- 给插件开放SQLite连接或任意Core内部API：无法稳定约束来源、权限、事务与迁移。
- 所有知识留在插件私有库：卸载/失效后不能通用阅读与导出。
- 插件等同MCP：无法覆盖UI贡献、安装生命周期、运行隔离和数据归属。
- 直接复用NSH主QuickJS上下文执行第三方代码：混淆UI与不可信执行边界。
- 从第一天承诺五端下载执行同一插件包：运行时、平台与分发条件没有证据。
- 为RSS、微信读书分别增加领域分支：不能验证通用扩展能力。

## 验收与未决定事项

EXT-P01–P08及新增EXT-P11–P13验证统一采集、恢复、权限、跨端贡献、独立包与SDK；真实服务/AI按EXT-P09/P10另加门槛。当前均未执行。

C-07已确认第一阶段开放第三方，并要求第一方功能围绕插件化。原先先自用的候选分期已由ADR 0003替代，Core数据所有权保持。首版是否交付RSS/微信读书、具体入口、运行时选型、插件市场和发布渠道仍未决定。

引入跨端插件能力可能增加验证工期；在对应实验前估算，不沿用原M-1时间框当作不变承诺。用户后续明确推进新阶段时按新指令更新范围，不以本ADR增加重复审批。
