# 多行 PDF 摘录原子收录本机记录

日期：2026-11-08。状态：独立 Core schema3 的复合锚点子项通过，生产与 NSH 阅读 UI 未通过。关联 [功能规格](../../docs/product/compound-pdf-capture.md) 与 [ADR 0017](../../docs/architecture/adr/0017-compound-pdf-capture.md)。

## 实际链路与固定输入

沿用固定 Rust 1.97.1、debug、锁定离线依赖及原生 PDFium 8125。真实两页英文 PDF 是既有 MIT 合成夹具，包含 CropBox 偏移及 Rotate 0/90；没有 WebView、外部账号或用户资料上传。

从页图的真实字形暗像素取得指针点，原生选区服务输出两段；可信适配器核对完整来源并构造版本 2 复合对象。仓库外公开 SDK 作者构建普通签名包，guest 先经 SelectionRead 取得全部段，再自行构造 CapturePropose。宿主显示完整引文、段数、页码和备注，批准绑定全部内容及顺序。

复现：先按 [原生 PDF 运行库准备](../pdf-provider/README.md)，再执行：

```sh
python3 experiments/capture-core/validate_compound.py
```

[JSON 证据](evidence/linux-compound-pdf.json) 包含开始/结束一致的源码指纹、稳定 native/Core 二进制 hash、SDK 源码与仓库外依赖图、全部结果。公开 SDK 不包含 Core、Host、SQLite、PDFium 或运行器实现。

## 验证结果

| 验证 | 实际结果 |
|---|---|
| 完整选区 | 两页实际原生多行选择均收录全部段；旋转页 engine 索引逆序仍按显式数组保留，不拼成 min/max 连续范围 |
| 单一提交 | 一次批准对应一个 capture ID、revision、回执及同事务操作/outbox/index；预览无回执，错误整体摘要不保存 |
| 完整哈希 | 第二段变化或合法重排不能复用旧批准；同操作换整体内容冲突；相同操作重试只返回原回执，独立用户意图仍分别保留 |
| 旧入口保护 | 复合提案 getter、旧完整查询和旧单段解析均明确拒绝复合记录，不能只审核或返回首段；新接口逐段返回完整来源 |
| 兼容 | 原 C0 文本、C1 单段 PDF 全链回归通过；V2 旧 archive 恢复后保持相同数据和回执；复合存在时必须输出 V3，伪装 V2 拒绝 |
| 完整恢复 | 混合文本/单段/复合 archive 空库恢复完全相等；原件逐字节相同；重新原生渲染和选择得到同样的复合锚点，全部段可准确解析 |
| 崩溃 | 新 CLI 执行复合提交 4 次、V3 恢复 3 次真实 exit(86)，重启只见空或完整事务；提交后回复丢失仍可查唯一整组回执 |
| 篡改 | 缺第二段、改顺序、首段投影不一致、归档版本降级、授权注入均拒绝；失败恢复无部分记录 |
| 生命周期 | 普通复合阅读包实际升级/私有迁移、成对回退和卸载；全部规范知识及段落顺序保持不变，卸载后仍可回源 |
| 旧数据迁移 | schema1/2 原子迁移到3，旧单段 JSON 与哈希有兼容 oracle；复合记录旧接口拒绝，未改旧实体 ID 或提交序列 |

验证器执行 314 条命令、286 项 CLI 场景及 8 项真实 native worker 场景。286 项包括原 C0/C1 的 198 项回归；31 次 CLI 真实退出中，原基线24次、新复合7次。原实验 Rust 测试共67项通过：旧46，复合契约8、复合Core6、复合Host7；ADR 0018 后纯契约26项移入根 core-api，实验保留41项，覆盖总量不变。复合Core测试另外运行10个提交/恢复/迁移子进程退出点，不与 CLI 计数混淆。

格式、全目标 Clippy 零警告、登记依赖图、仓库外 SDK 作者编译与 Clippy 通过。C3初轮没有新增生产根 Workspace 成员；随后 ADR 0018 新增 core-api，依赖与闭包已登记。

## 联调发现与修复

复合提案最初仍允许 `draft()` 返回首段，可能令旧调用方审核首段却批准整体 hash。现改为显式错误，必须读取完整复合对象；旧 Core 查询同样拒绝，而完整接口显式返回全部段。

真实混合资料联调还发现，原生全库磁盘校验在每个能力回调内重复执行，耗尽既有 Wasm 250ms 执行期限。现将冻结选段校验放在 native 准备阶段并复用有界响应，执行期间每次仍检查实时会话/授权，提交时由 Core 重新完整验证。不放宽 VM 期限，不移除最终校验；额外测试实际损坏原件，分别证明执行前和批准后提交前均拒绝且无摘录/回执写入。完整 native 准备的耗时和可抢占性不因此获得保证。

## 边界与后续

复合对象保留2–8段及明确 LF 展示分隔符；每段原文、版本和范围独立可核对。显示分隔符不是新增的原 PDF 字符。完整请求与响应按真实4KiB预算验证，超限拒绝而非截断。资格上限不是产品范围缩减，长选区、跨页能力仍需后续协议与体验验证。

受限 LTR 分段不等于全部 PDF canonical 阅读顺序。此次真实 PDF 为英文，中文/复杂字体/排版、跨页指针、NSH 窗口/捕获、键盘/触控/可访问性与五平台均未验。原生服务供给的导入仍不是正式 library 插件；生产 Core/SDK/安装器与完整阅读旅程继续按原计划推进。

schema3 复合记录在旧字段保留首段兼容投影，校验强制其等于第一段，完整锚点仅由 compound 表示。旧接口拒绝该记录，新接口必须处理完整对象；不能据投影声称整条引用已读取。V3 恢复和当前 source 指纹另行记录，不将较早 JSON 当作新实现的当前证据。


## Core API 落位后的复验

[ADR 0018](../../docs/architecture/adr/0018-core-api-contract-source.md) 将三份公开契约迁入 [core-api](../../crates/core-api/README.md)，实验旧路径仅转发。迁移前后实现文件逐字节一致，摘要对照见 [迁移证据](evidence/linux-core-api-migration.json)。SDK 直接导出新权威源，仓库外作者通过 Cargo 依赖别名保持原 import；没有 Core/Host/数据库源码依赖。

根 clippy/test 通过，包含26项捕获契约与35项原策略测试；实验41项 Core/Host 测试、42项架构守卫回归通过。完整 C3 复验再次通过314条命令、286项 CLI 场景及8项 native 场景，已更新同一 [当前 JSON](evidence/linux-compound-pdf.json)，其源码指纹包括 core-api 源码、测试和 manifest；旧 C0/C1证据仍按各自生成时版本理解。该轮生产落位仅指公开契约，SQL/CAS和用例当时仍在独立实验；其后 ADR 0019 的当前迁移结果另见下文。
